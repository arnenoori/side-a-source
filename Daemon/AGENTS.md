# Daemon (`sidead`)

The headless Linux daemon: it pairs with the phone, hosts sessions under tmux, lists accounts and their limits, tunnels through the relay and sends push, and is packaged (`docs/ports/linux.md`, `docs/ports/windows.md` for WSL 2; plan in `docs/ports/windows-linux-prd.md`). It offers permission requests from Claude Code once `sidead hooks on` has added the hook, moves sessions between linked computers (directly or through the relay) and keeps or sends standby checkpoints, and not yet questions and plans, Codex requests, worktrees, forking, attachments, queued follow-ups, the terminal view, Autopilot or trades (the list is in `linux.md`). A separate package so SwiftNIO, NIOSSL and swift-certificates stay out of the Mac and iOS dependency graphs.

- It reaches the repository root through the symlink `Daemon/Dependencies/side-a`. Do not replace it with a path of another name: a path dependency's identity is its directory name, which differs in every worktree.
- Check on Linux with `scripts/linux-check.sh` (Docker; `--here` on a Linux host). It builds the protocol package, `SideACore` and this package, runs their tests and starts `sidead`. `swift test --package-path Daemon` also works on a Mac.
- Reuse, do not rewrite: HTTP parsing and responses are `SideACore`'s `HTTPParser` and `HTTPResponse` (not NIOHTTP1), wire types are `SideAProtocol`, and the key pin is `SPKI.hash` from the protocol package. Routes live in `Sources/SideADaemonKit/Routes.swift`; a route answers only what its capability says.
- Tests start the server on port 0 and pin the key like the phone does. Never use a fixed port in a test, and do not read or write the real `~/.claude` or `~/.codex`.
- Anything platform-specific (secrets, power, processes, autostart) goes behind a small protocol so the Mac app can share the code later; see the plan in `docs/structure.md`.
- Sessions (`SessionServices`, `HostedTmux`, `SessionBridge`) run the Mac's Python bridge (`bridge/`, found beside the binary at `share/side-a/bridge` or in a checkout) and a tmux on Side A's own socket. Start programs with `Run.process`, never Foundation's `Process`: on Linux `Process` did not notice `tmux new-session -d` exit. `Run.process` also closes every descriptor but stdin, stdout and stderr in the child (`addclosefrom_np` on Linux, `POSIX_SPAWN_CLOEXEC_DEFAULT` on Darwin): NIO sets no close-on-exec, and a tmux server that kept the listener held the port after the daemon stopped. What needs a hook the daemon doesn't run is not offered; add a capability only with the route that serves it.
- A trial daemon beside a real Side A: on macOS (dev only) the daemon finds its data folder from the real home, not `$HOME`, and by default shares the `tmux -L sidea` server. Set `XDG_DATA_HOME` and `SIDE_A_TMUX_SOCKET` to keep a trial run apart.
- Permission requests (`Approvals`, `HookSocket`, `Hooks`, `RelayLink+Requests`) reuse the Mac's `bridge/island_hook.py` and `SideACore`'s `IslandRequest`, `RemoteAnswers`, `AllowGate` and `IslandAnswer`: put a rule there, not here. `sidead hooks` is the only thing in the daemon that edits a user's file (`settings.json`, through the bridge's `island on --permission-only --claude-dir`), so keep it explicit, marked and removable, and keep the hook failing open. The stand-in agent is `Tests/Fixtures/fake-claude-permission.py`.
- `scripts/linux-e2e.sh` (Mac only) is the end-to-end check: a sidead in a container, driven by `Daemon/Probe`, a client built on `SideARemoteKit`, with `Daemon/Tests/Fixtures/fake-claude-live.py` as the agent. Never point a test at the real `claude` or `codex`.
- Accounts (`Accounts.swift`) are folders run with `CLAUDE_CONFIG_DIR`; the usage read-out never refreshes a login, and nothing in the daemon signs in. A `.credentials.json` or Codex `auth.json` is moved only with a moved session (`Moves+Logins.swift`), never from or into `~/.claude` or over an existing one. `bridge/hostos.py` `claude_dirs()` is how the bridge sees every account's sessions.
- Moves (`Moves*.swift`, `MoveServices`, `MovePeer`, `PeerClient`, `Computers`) port the Mac's `Moves`: the order of events is `SideACore`'s `MoveJournal` and the files are `bridge/move.py`'s, so change a rule there and on the Mac first, then here. Ids from another computer go through `wellFormed` (`mv-`, `sb-` for a checkpoint, and the conversation) before they name anything. Tests run two daemons with separate homes, state and tmux sockets (`MoveTests.swift` and the `extension MoveTests` files, so they stay serialized). Standby is `Moves+Standby.swift`, both roles; the Mac's switches are `MoveSettings` (`sidead config`), read from disk each time, and an unreadable file turns everything off. Where this differs from the Mac on purpose (Run Here refuses when the other computer says it runs there; a copy is refused without a login; Accept Sessions' second sentence names `sidead config`), `docs/ports/linux.md` says so.
- The relay (`RelayHTTP`, `RelayTunnel`, `RelayLink`) is the Mac's protocol on NIO. Everything in `RelayTunnel` runs on its one event loop; use `ChannelOptions.tcpOption(.tcp_nodelay)`, not `socketOption` (it failed with EACCES on Linux). `SIDEAD_TUNNEL_TRACE=1` logs every frame to stderr. `PeerTunnel` is the other end, the phone's role, for a move to a linked computer whose addresses don't answer: one WebSocket per linked computer, each request a stream spliced to a socket pair the pinned TLS runs on. Both ends share `TunnelSplice` (the credit window); change flow control there, once. The tests' `StubRelay` serves both ends and checks the device credential against the device list the Mac side sent.
- Packages come from `scripts/package-sidead.sh` (Docker; tarball and `.deb`); `scripts/linux-e2e.sh --package TARBALL` installs one in a clean Ubuntu and runs the probe against it. The files they ship are in `Daemon/Packaging`.
