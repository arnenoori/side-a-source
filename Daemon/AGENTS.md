# Daemon (`sidead`)

The headless Linux daemon: it pairs with the phone, hosts sessions under tmux, lists accounts and their limits, tunnels through the relay and sends push, and is packaged (`docs/ports/linux.md`, `docs/ports/windows.md` for WSL 2; plan in `docs/ports/windows-linux-prd.md`). It does not yet offer permission requests, questions and plans, worktrees, forking, attachments, queued follow-ups, the terminal view, Autopilot or trades (the list is in `linux.md`). A separate package so SwiftNIO, NIOSSL and swift-certificates stay out of the Mac and iOS dependency graphs.

- It reaches the repository root through the symlink `Daemon/Dependencies/side-a`. Do not replace it with a path of another name: a path dependency's identity is its directory name, which differs in every worktree.
- Check on Linux with `scripts/linux-check.sh` (Docker; `--here` on a Linux host). It builds the protocol package, `SideACore` and this package, runs their tests and starts `sidead`. `swift test --package-path Daemon` also works on a Mac.
- Reuse, do not rewrite: HTTP parsing and responses are `SideACore`'s `HTTPParser` and `HTTPResponse` (not NIOHTTP1), wire types are `SideAProtocol`, and the key pin is `SPKI.hash` from the protocol package. Routes live in `Sources/SideADaemonKit/Routes.swift`; a route answers only what its capability says.
- Tests start the server on port 0 and pin the key like the phone does. Never use a fixed port in a test, and do not read or write the real `~/.claude` or `~/.codex`.
- Anything platform-specific (secrets, power, processes, autostart) goes behind a small protocol so the Mac app can share the code later; see the plan in `docs/structure.md`.
- Sessions (`SessionServices`, `HostedTmux`, `SessionBridge`) run the Mac's Python bridge (`bridge/`, found beside the binary at `share/side-a/bridge` or in a checkout) and a tmux on Side A's own socket. Start programs with `Run.process`, never Foundation's `Process`: on Linux `Process` did not notice `tmux new-session -d` exit. What needs a hook the daemon doesn't run is not offered; add a capability only with the route that serves it.
- `scripts/linux-e2e.sh` (Mac only) is the end-to-end check: a sidead in a container, driven by `Daemon/Probe`, a client built on `SideARemoteKit`, with `Daemon/Tests/Fixtures/fake-claude-live.py` as the agent. Never point a test at the real `claude` or `codex`.
- Accounts (`Accounts.swift`) are folders run with `CLAUDE_CONFIG_DIR`; the usage read-out never refreshes a login, and nothing in the daemon signs in or copies a `.credentials.json`. `bridge/hostos.py` `claude_dirs()` is how the bridge sees every account's sessions.
- The relay (`RelayHTTP`, `RelayTunnel`, `RelayLink`) is the Mac's protocol on NIO. Everything in `RelayTunnel` runs on its one event loop; use `ChannelOptions.tcpOption(.tcp_nodelay)`, not `socketOption` (it failed with EACCES on Linux). `SIDEAD_TUNNEL_TRACE=1` logs every frame to stderr.
- Packages come from `scripts/package-sidead.sh` (Docker; tarball and `.deb`); `scripts/linux-e2e.sh --package TARBALL` installs one in a clean Ubuntu and runs the probe against it. The files they ship are in `Daemon/Packaging`.
